# Recurring Bug Classes

Each of these has bitten this codebase **more than once**. Grep for the signature before you write, and again before you claim a fix is done.

**🤖 = enforced by `scripts/check_recurring_bugs.py`** (runs in CI on changed files). Everything unmarked is enforced only by you remembering to read this file — and the recurrence counts below were all recorded *after* the class was documented here, so assume prose alone does not hold. If you fix a class that recurs again, the durable move is a check in that script, not another paragraph here.

Currently automated: `date.today()` write-anchor, raw `%s` placeholder, missing `live_datasource` test, `x != x` NaN test in SQL, multi-word `::` cast, skip-path-stamped-as-success (`.ts`, `check_skip_not_success`). Also automated, in `verify-gate.mjs` rather than `check_recurring_bugs.py`: unmeasured signal/scoring changes require backtest evidence before "done" is accepted. Deliberately not automated: `float(x or 0)` — measured at 50 matches repo-wide, mostly legitimate `None`→0 on DB aggregates; catching it needs type information the script doesn't have.

## Dates & scheduling

| Signature | Why it breaks | Recurrences |
|---|---|---|
| `date.today()` / `datetime.now()` as an **exact-match write target** (`WHERE date = ?`) | Post-close jobs now finish after midnight IST, so "today" resolves to a day with no grid row → UPDATE matches 0 rows, silently. Use `as_of.logical_trading_date()`. | 11 files |
| 🤖 `date.today()` anchoring a `CASE WHEN date >= x ELSE NULL` guard | On any weekend/holiday the anchor matches nothing and the `ELSE` **nulls the column's entire history**. Anchor to `MAX(date) FROM stock_ohlcv`. | 10 |
| Raw `daysStale()` on a freshness check | Monday morning reads Friday data as 3 days stale. Use `tradingDaysStale()`. | 4 |
| Hand-rolled "step back N weekdays" | Skips no holidays, so `--days 90` covers 87 sessions. Use `as_of.trading_days_back()`. | 2 |
| A `cronPattern` mirrored into `jobRegistry.ts` / `monitorScripts.ts` | Drifts from the real registration → phantom "late"/"stale" alerts forever. Guarded now by 5 mirror-consistency test suites — keep them passing. | 6 |
| A coverage/completeness **ratio** (not just a staleness gap) computed over a window that includes **today** | Same root cause as `daysStale()` above, different shape: if today's rows are written by one job (e.g. a morning scan) and enriched by a later one (e.g. an evening ML-scoring pass), a same-day denominator reads as a false collapse for the whole gap between the two — every weekday, not just Mondays. `technical-signals-freshness-coverage`'s win_probability ratio had exactly this bug even after its *staleness* half was already fixed for the Monday case (2026-08-10) — fixed 2026-08-11 by measuring the ratio over the most recently **completed** day (`date = MAX(date) WHERE date < today`), not "last N days" inclusive of today. | 2 |

## NaN & null

| Signature | Why it breaks |
|---|---|
| `float(x or 0)` / `int(x or 0)` on a model-output column | **NaN is truthy** — `nan or 0` is `nan`. Use `math.isfinite`, and **skip** rather than coerce to 0 (coercing fabricates the worst possible score). |
| 🤖 `x != x` to detect NaN in Postgres | Postgres defines `NaN = NaN` as TRUE for total btree ordering. The IEEE self-inequality matches nothing and reports "clean". (In plain Python `x != x` is correct and is used on purpose in ~10 fetchers — the checker only flags the SQL form.) |
| A NaN-detection test on SQLite | SQLite coerces NaN to NULL on insert, so the test passes against unfixed code. Use a throwaway Postgres schema. |
| `ORDER BY col DESC` with possible NaN | Postgres sorts NaN **highest** — NaN rows rank #1. Wrap in `NULLIF(col, 'NaN'::float8)`. |
| Fixing NaN at the source | Does **not** clean rows the bug already wrote. `run()` purges only the `computed_at` it is currently writing; 13,505 poisoned rows survived a source fix for weeks. |

## SQL dialect (`db_compat` / `sqlTranslate`)

| Signature | Why it breaks |
|---|---|
| 🤖 Raw `%s` placeholders in a Postgres branch | Bypasses `translate()`, which expects `?`. psycopg2 throws on the literal `%`. | 
| 🤖 Multi-word casts (`::double precision`) | `stripPgCasts` only matches single-token type names; leaves a dangling ` precision` on the SQLite path. Use `::float8`. (Checker covers `.py` only — `sqlTranslate` itself is `.ts` and is not scanned.) |
| `STDDEV`, `DISTINCT ON`, `NOW()`, `ANY(ARRAY[])` | Postgres-only. On the SQLite fallback the whole query fails and the caller silently gets `{}` — which can **disable a gate entirely** rather than error. |
| `pd.read_sql(raw_string, conn)` containing a literal `%` | Different execution path from `db_compat`; the `%` is read as a param marker. Wrap in `sqlalchemy.text()`. |
| `CREATE TABLE IF NOT EXISTS` after adding a column | No-ops on an existing table. Needs an explicit `safe_alter`. |
| A column type assumed from `db.ts` | `db.ts` is the SQLite schema-of-record; live Postgres has native `DATE`/`TIMESTAMPTZ` columns. Check `information_schema.columns`. |
| A bulk `unnest($1::text[], $2::int[], ..., $n::text[][])` insert with one array-*typed* column alongside N scalar-array columns | `unnest()` flattens **every** dimension of a multidimensional array argument in row-major order — it does not treat the inner arrays as "one array value per output row" the way the sibling scalar-array params behave. Found in `greenfield/packages/db/src/stage5-repo.ts`'s `bulkInsertRecommendations` (`recommendation.veto_reasons text[]`, 2026-08-14): every `veto_reasons` was `[]`, which happened to form a valid rectangular `text[][]`, and Postgres raised `column "veto_reasons" is of type text[] but expression is of type text` rather than silently misrouting rows — but a same-length *non-empty* set of arrays would not error, it would silently change the output row count instead (numRows × arrayLen rows, not numRows). Fix: pass the array column as `jsonb[]` (a scalar type as far as a 1-D array parameter is concerned, so it unnests one value per row correctly) and reconstitute the real array inside the `SELECT` with `ARRAY(SELECT jsonb_array_elements_text(col))`. Check any future bulk-unnest writer touching an array-typed column this way — `signal.targets numeric(18,4)[]` (GREENFIELD_BUILD_SPEC.md C6) is the next one likely to hit this. |

## Writes & keys

- **A one-shot script calling `openRun` must seed its own `job_definition` row first (`ON CONFLICT DO NOTHING`), the same as every sibling script in the same directory.** `greenfield/packages/ingestion/src/stage5/record-shadow-preregistration.ts` skipped this step (2026-08-14) while every other Stage 5 script — `run-ranker.ts`, `run-divergence-analysis.ts`, `promotion-gate.ts` — has it; `ingestion_run.job_id` FKs to `job_definition`, so its first real invocation threw `ingestion_run_job_id_fkey` on the very first line of actual work. Compounded by a second bug in the same file: the failure happened OUTSIDE the function's own try/catch (there wasn't one — errors just propagated to the top-level `main().catch()`), which logs and sets `process.exitCode` but never calls `pool.end()` — an open `pg.Pool`'s idle-connection timers keep the process alive, so instead of exiting with a clear error the script hung until an external timeout killed it. Live-caught only because the script was actually run end-to-end (not just typechecked/unit-tested) — a code review of the file in isolation would not have caught either half without noticing job_definition's absence relative to its siblings. Fixed by adding the seed and wrapping the body in try/finally with `pool.end()` in the finally, guaranteeing pool cleanup on every path, not just the success path.
- **Any table written as "today's full recomputation" needs a purge of rows the run did not produce**, not just an upsert. A row that a newly-added gate now excludes keeps its stale row and stays visible to every consumer. (3 recurrences: `unified_recommendations`, `intraday_outcome_resolver`, `stock_event_triggers`.)
- **A backfill loop that gates re-selection on one of several columns it fills** permanently excludes rows that got the first column filled but not the rest. (2 recurrences.)
- **A provider-issued id needs the provider in the PK.** (4 recurrences — see `data-sources.md`.)
- 🤖 **A job whose skip path falls through to the same "completed/success" handler as a real run will erase that day's failures.** The `technical-signals` worker returned early outside market hours; the post-close runs then stamped `success` over 13 genuine failures earlier the same day, every day, for two sessions. Have the skip path return a marker (`{ skipped: true }`) and make the success handler decline it. Same class as the "success heartbeat on a step that wrote nothing" warning in `measurement.md`. **Recurred 5 times, not once**: fixing `technical-signals` (2026-08-12) and then writing the static check for it (`check_skip_not_success` in `check_recurring_bugs.py`) immediately found 4 more live, previously-unknown instances in the same file, same shape, same day — `intraday-fetcher`, `live-screener-collect`, `trendlyne-intraday-scan`, and `trendlyne-checklist-cycle` (the last one found by the checker itself, not by manual review, after a bare-eyes pass of the surrounding code had already stopped at 3). A code-review pass that finds N instances of a class should not be trusted as complete; write the check and let it look everywhere the class's own shape can hide.
  **Sixth recurrence, 2026-08-17 — and this one the static check structurally could not see.** The five above were hand-rolled handlers inside `queues.ts`; this was `jobs/registerJob.ts`'s **SHARED** `.on('completed')` handler, so *every* job routed through that helper was missing the guard at once. `check_skip_not_success` only fires when the processor and its `completed` handler live in the same file, and here they are split across `jobs/*.jobs.ts` and `jobs/registerJob.ts`. **`confluence-compute` is why it mattered**: it no-ops for ~9 hours a day, so a genuine failure inside its work window was overwritten by the next out-of-window skip within 30 minutes — on a job marked `critical`. **When you write a static check for a class, ask what file layout makes the class invisible to it, and say so in the check's own comment** — otherwise "the checker is clean" is read as "the class is extinct".

- **A lateness/deadline branch anchored on the CURRENT cadence boundary can never fire, for any input.** Found 2026-08-17 while negative-controlling the fix above. `jobHeartbeat.ts`'s `everyMs` branch computed the deadline from the most recent cadence boundary, so `now - boundary` is **by construction** less than `everyMs`, and any `graceMinutes` larger than the cadence put the deadline permanently in the future. **All three `everyMs` entries were in that state** — `news-sentiment` and `trendlyne-intraday` at a 15-minute cadence against a 45-minute grace, `confluence-compute` at 30. Proven rather than reasoned: a heartbeat seeded **7 months stale** still reported `late=false` for `news-sentiment`, which is `critical`. Fixed by anchoring on the most recent boundary whose grace has **already expired**. Same family as this file's "monitor that fires on EVERY run carries no information" entry, inverted — a monitor that can never fire carries none either, and is harder to notice because silence reads as health. **Tell:** any deadline arithmetic where the grace period can exceed the interval it is measured against.

- **`dict.get(key, default)` returns the default only when the key is MISSING — not when it is present with an explicit null.** `trendlyne_adv_tech_fetcher.py` did `params.get("volume_analysis", {})`; Trendlyne sends that key present with a JSON `null`, so `.get` returned `None` and the next `.get`/iteration raised `AttributeError: 'NoneType' object has no attribute 'get'`. It killed the whole `trendlyne-midweek` job **every Tuesday since 2026-08-04**, while the heartbeat's truncated error text pointed at unrelated upstream 405s. Eight sibling keys across two fetchers had the identical shape and were all converted to `.get(k) or {}` / `or []` — fix the shape, not the one key that happened to crash first. **Tell:** any `.get(k, {})` / `.get(k, [])` against a third-party payload you do not control; a provider is free to send `null` where it used to send nothing, and that is not the same thing.

- **An import-time environment variable set inside a function is set too late, and an `os.environ` assertion cannot catch it.** `huggingface_hub` snapshots `HF_HUB_OFFLINE`/`HF_HUB_DISABLE_PROGRESS_BARS` into module constants **at import**, so setting them inside a loader function has no effect on the already-imported library. Both FinBERT loaders (`nlp_engine.FinBERTInference`, `finbert_scorer.load_model`) therefore round-tripped to the Hub on every process start despite a complete 836MB local cache, making every `runPython()` call of `finbert_news_sentiment.py` log as "finished successfully with warnings/stderr output" (268 bytes of stderr → 0 after the fix; predictions unchanged). Fixed by moving the `setdefault` to module top — `setdefault`, not a hard set, so `HF_HUB_OFFLINE=0` still allows a cold-cache download. **The guard test must assert the LIBRARY'S constant (`huggingface_hub.constants.HF_HUB_OFFLINE`), not `os.environ`**: `setdefault` sets the env var whether it runs before or after the import, so an `os.environ` assertion passes against the broken ordering too. Negative-controlled — setting it after the `transformers` import leaves the constant `False`.

- **A monkeypatched stub whose signature is hand-copied from the real function is a second declaration of the same interface, and nothing keeps the two honest.** Hit **twice on 2026-08-17**: `test_trendlyne_fundamentals_fetcher`'s `_load_stocks` lambda still had the old signature, so `main()`'s new `skip_done_for_date` kwarg `TypeError`ed on the first call; and `_CaptureDB.query_all` in `test_live_datasource_intraday_fetcher.py`, the same shape, had been broken for **7 days**. The `_load_stocks` lambda has now drifted from the real signature twice. **Tell:** a `monkeypatch.setattr(mod, name, lambda ...)` whose parameter list is written out by hand — prefer `functools.wraps`/`inspect.signature`-checked fakes, or accept `*args, **kwargs` so a new kwarg cannot break the stub while the real call site is fine.
- **A freshness monitor that probes a job's OUTPUT TABLE reports a gated job as "stale" every time the gate correctly rejects.** `strategy-optimizer` writes to `screener_weight_history` only when the optimised weights beat baseline on held-out data, so two consecutive correct rejections (2026-08-09, 2026-08-10) got reported as "stale since Aug 03" while the job ran clean weekly. Derive last-run from the LATEST of the output probe, the stored `_ran_at`, and `job_heartbeat.last_success_at` -- never the output table alone. Applies to any promotion-gated script.
- **A data-quality check that fires on a bare count > 0 will fail on correct data.** `stock_delivery_data.trades = delivery_qty` is legitimately true for an illiquid name (ASTAR: 4 shares in 4 trades, 100% delivery). Compare a SHARE of rows against a floor sized to the real defect (that one was 100% of 664,006 rows, so a 5% floor has enormous margin). A check that cries wolf on real data stops being read -- same argument as the ungated live-network test in `data-sources.md`.

- **A column referenced in SQL is not a column that exists.** `quant_scores` is `PRIMARY KEY (symbol)`, one row per symbol, and has no `date` column -- but two queries added in one sweep wrapped it in `ORDER BY date DESC` (a latest-per-symbol window that was never needed). One aborted the entire technical scan for two days; the other sat behind `.catch(() => null)` writing NULLs in silence. Check `information_schema.columns` before ordering/partitioning by a date column, and grep **every** reader of the table -- this arrived twice in the same commit.
  **Recurred a third time, 2026-08-13, same file family:** `scoring_engine.py`'s `_log_recommendations` batched price/ATR lookup (added 2026-08-07, per its own comment, specifically to fix an *earlier* incarnation of this exact null-enrichment problem) added `(SELECT qs.rank_composite FROM quant_scores qs ... ORDER BY qs.date DESC LIMIT 1)` as a correlated subquery inside a larger 5-column `SELECT`. Because it's one statement, Postgres aborts the *entire* query on `UndefinedColumn`, not just that subquery -- and the whole thing sits behind a blanket `except Exception` that only logs a warning. Live-confirmed 2026-08-13: 100% of `recommendation_log` rows from `scoring_engine` had NULL `entry_price`/`target_1-3`/`stop_loss`/`news_sentiment_score`/`quant_score` -- not just the `rank_composite` column the broken subquery directly touched, but everything else in the same batched query too, silently re-breaking the exact `entry_price` null-enrichment bug the 2026-08-07 comment says was fixed 2026-07-30. **Tell that made this findable:** the fetcher's own log line, `[ScoringEngine] price/ATR lookup for recommendation_log failed (entry_price will be null): column qs.date does not exist` -- printed, but to stdout only, with no alerting/freshness check watching for it, so it ran silently for however long the 2026-08-07 change had been live. Fixed by dropping the bogus `ORDER BY qs.date DESC LIMIT 1` (quant_scores has no history, one row per symbol, nothing to order). Live-verified: re-ran `process_scoring()`, `recommendation_log` rows for the day went from 0/1584 to **1,492/1,584 (94%) with `entry_price`/`quant_score` populated**. **One query touching a nonexistent column doesn't just null its own output column -- it can null every sibling column selected in the same statement.** When a batched multi-column lookup like this fails, don't assume partial data; check whether the whole `SELECT` aborted.

- **`except Exception: pass` around a failed statement does NOT contain the failure on Postgres — it aborts the whole transaction, and every later statement on that connection dies with `current transaction is aborted`.** The real error is swallowed; only the cascade surfaces, several calls away, naming a table that is perfectly fine. On SQLite the same code is harmless, which is why every instance below survived: the graceful-degradation handler was written and tested against a dialect where a failed statement is local. **Five separate instances found in one day (2026-08-16)**, all pre-existing, all invisible until the suite ran against Postgres:
  1. `backfill_ohlcv._load_holidays()` — `SELECT ... FROM market_holidays` inside `except Exception`. Missing table ⇒ the *following* `_upsert()` executemany failed instead.
  2. `chatbot/tools/news_tool.get_news_sentiment()` — queries `news_sentiment_items`, then falls back to `news_articles` inside `except Exception: pass`. **The fallback was unreachable on Postgres for its entire life**: the first query's failure aborted the transaction, so the fallback failed too and the function returned empty rather than degrading. A resilience path that cannot run is worse than no path, because it reads as covered.
  3. `mf_holdings_fetcher.ensure_schema()` — `CREATE TABLE` then `ALTER TABLE ... ADD COLUMN` in `try/except: pass`. The ALTER fails once the column exists, aborting the transaction, and the trailing `con.commit()` **silently discards the CREATE TABLE**. Harmless where the table already exists (which is why it survived); on a fresh database the table is simply never created. 9 files repo-wide share this `CREATE`-then-`ALTER` shape; 3 lack a commit in between.
  4. The same shape again in the chatbot tools, where each tool wraps its queries in `except Exception` — one missing table poisoned every subsequent query in the same agent turn.
  5. `mc_ohlcv_backfill.upsert()` — different root cause, same family (see the engine-bypass entry below).
  6. **`unified_ranker.run()` — the worst instance yet, found 2026-08-17.** This file has **33** `except Exception: print(...)` blocks, most of them a read whose own docstring promises it "degrades to {} if the table is absent". On Postgres the first one poisons the connection and every later read fails — and those failures are swallowed by the same pattern, so nothing errors and nothing alerts. Reproduced: one missing advisory table (`stock_event_triggers`) made the ranker print 10 consecutive "unavailable" lines, classify its **entire universe as Hold with 0 bull/bear counts**, and **exit 0**. The cascade is not N bugs; only the FIRST line names a real cause, the rest say `InFailedSqlTransaction`.
  **Fix at the source, not the call site:** `conn.rollback()` inside the `except` before continuing, but ONLY where the function is read-only or owns its transaction — rolling back inside a shared helper can discard a caller's pending work, which is why `_load_holidays` got a fixture fix instead. **As of 2026-08-17 there is also a generic backstop**: `db_compat.ConnWrapper.execute`/`executemany` roll back before re-raising (`_usable_after_failure`), which restores the sqlite3 contract the class advertises it mimics. It is deliberately gated on `_transaction_is_aborted()` — asking psycopg2 for `TRANSACTION_STATUS_INERROR` rather than inferring from the exception — precisely because of the shared-helper warning in this paragraph: a `translate()` rejection or a `build_params()` error fails the statement WITHOUT aborting anything, and there the caller's pending work is still committable and must not be discarded. The backstop does not make the per-site guidance obsolete: it keeps the connection alive, it cannot restore the data the swallowed read was supposed to return. For `CREATE`-then-`ALTER`, commit the CREATE first. **Tell:** an error naming a table/column that demonstrably exists, or a "graceful" fallback that returns empty instead of falling back. Before believing the named statement is the culprit, look for an earlier swallowed one on the same connection.

- **A function that takes a `conn` argument and then ignores it silently defeats every caller's isolation.** `mc_ohlcv_backfill.upsert(conn, rows, overwrite)` used `get_engine().raw_connection()` unconditionally on its Postgres branch — a separate pool that does **not** carry the caller's `search_path`. Every row landed in `public` no matter what schema the caller was scoped to. Live-caught 2026-08-16: the fetcher's own live_datasource test wrote **252 real RELIANCE bars into `stock_ohlcv`** while reading back through its own throwaway schema and seeing nothing — surfacing as the maximally-confusing `upsert() reported success but wrote no row`. On a developer box that target is PRODUCTION; it was caught only because the run was pointed at a replica. Same family as this file's "writes through one engine, reads through another" test entry, but in **production code**, where it is worse: the `conn` parameter is a lie, and no test fixture, schema scoping or transaction the caller sets up has any effect. Fixed by borrowing the caller's DBAPI connection when it has one and committing through its SQLAlchemy Connection so transaction state stays consistent. **Tell:** grep any function whose signature takes `conn`/`con` for `get_engine()`, `connect()` or a module-level pool inside its own body — if both appear, the argument is decorative.

- **Restricting a universe upstream** re-tunes every absolute threshold downstream. An engine fix that deflates one score collapsed actionable Buys 612 → 22 under an unchanged floor.

## Models & measurement

- ✅ **RESOLVED 2026-08-12, re-verified live 2026-08-16 — do not re-open this as a bug.** The UNION was **removed**, not repaired, because it was a category error rather than a gap: an AI/screener signal has no `RSI_DIVERGENCE`-style pattern type to weight, and `unified_signal_outcomes` has no column that could supply one. Per-source learning already has its own correct home — `update_source_weights()` reads `unified_signal_outcomes`, groups by `(signal_source, regime, sector)` and writes `signal_source_weights`. **Live-verified 2026-08-16: 219 rows across 6 sources, `AI` among them with 45.** Nothing stopped being learned from; `processed` merely stopped overstating what the function had used. The N+1 in the same function is also fixed (regime/sector lookups batch-loaded up front). **This entry cost real time on 2026-08-16**, when it was read as an open item needing backtest evidence and reported as such twice before the source was checked — the lesson being this file's own: a rule entry is a claim with a date on it, and the code is the authority. Original entry follows for the pattern, which is still worth recognising elsewhere.
- **A UNION half that supplies NULL for the column the consumer keys on is inert, and its row count hides that.** `reward_engine.py`'s `update_weights()` unions `signal_outcomes` with `unified_signal_outcomes`, but the second half selects `NULL AS signals_json` while weights are only ever accumulated per signal *type* parsed out of that column (`_parse_signal_types(None)` → `[]`). Every row that half contributes is counted in the returned `processed` figure and then silently discarded at the accumulate step — so the reward engine **cannot learn from AI/QUANT outcomes at all**, for any source, however many rows accumulate. It looks alive from the outside: the query returns rows, `processed` grows, the job logs success. Found 2026-08-12 only because a test written for a *different* bug (the `NOT IN ('TECHNICAL')` case-collision, below) had a control assertion that a non-technical source *should* change the weight — and it didn't. **Write the control assertion.** A test that only checks "the thing I excluded stayed out" passes identically against a filter that excludes everything. Pinned by `test_unified_signal_outcomes_half_cannot_affect_weights`; making it functional is an RL-weighting change and needs backtest evidence first.
- **An enum-ish column with two spellings differing only by case will silently defeat an `IN`/`NOT IN` list.** `unified_signals.signal_source` carried `technical` (technical_analysis_engine.py) and `TECHNICAL` (technicalSignalsService.ts) — two different producers. `reward_engine.py` excluded `NOT IN ('TECHNICAL')`; when Cluster B-lite folded the Python engine in under the lowercase spelling, 25,740 rows began passing a filter written to stop them and nothing errored. Renamed to `technical_scan` (migration `1786930000000`) and now guarded by the `signal-source-case-collision` data-quality check. Same family as the composite-key collisions in `data-sources.md`: the defect is that two things that must be distinguishable aren't, and no constraint expresses it.
  **Recurred 2026-08-13 in a second table, worse in shape**: `screener_catalog`'s PK is `(screener_id, source)`, and three independent writers (`screener_catalog_enricher.py`, `trendlyne_screener_discovery.py`, `unified_ranker.py`'s CSV loader) each picked their own casing for `source` (`trendlyne`/`Trendlyne`, `moneycontrol`/`MoneyControl`, `etnow`/`ETnow`). Because the PK includes the differently-cased string, the rows never collide and both survive forever — worse than the `signal_source` case, where at least `IN`/`NOT IN` failed loudly enough to be traceable. Measured: 1,707 of 2,539 rows (67%) belonged to a screener_name with >1 catalog row, and 212 of those disagreed on `signal_bias` — e.g. `'All Stars: High Scorers Across Metrics'` was `bullish` under `trendlyne` and `bearish` under `Trendlyne`, and which one a stock got depended on which producer's `screener_id` slug its `trendlyne_screener_stocks` membership row happened to carry (the two producers ALSO slugify screener names differently — one strips punctuation, one keeps it — so this isn't even a clean `LOWER(source)` merge; the `screener_id`s differ too). Separately, two readers (`intraday_ranker.py`, `movement_predictor.py`) joined with exact-case `sc.source='trendlyne'`, silently missing 25–49% of the catalog depending on source. Fixed by harmonizing `signal_bias` across every row sharing an identical `screener_name` (script: `fix_screener_catalog_source_casing.py`, dry-run reviewed before `--apply`) rather than merging rows by `screener_id` (which would have required resolving the slug mismatch too) — lower-risk, and every membership row now resolves to an agreeing label regardless of which producer's ID/casing it references. **Tell:** `SELECT screener_name, count(DISTINCT signal_bias) FROM screener_catalog GROUP BY 1 HAVING count(DISTINCT signal_bias) > 1` — re-run this before trusting any screener-consensus number, not just once after a producer is added.

- **An upsert keyed on a derived value (not the provider's own id) silently discards the provider's id on every re-derivation, with no error.** `trendlyne_screener_discovery.py`'s `upsert_screener()` writes `trendlyne_screeners` `ON CONFLICT(screener_id) DO UPDATE` where `screener_id` is `name.lower().replace(' ', '-')...` — a slug derived from the screener's *name*, not its numeric `screenpk`. Trendlyne periodically reassigns a new `screenpk` to the same logical screener (same name, same slug) as it refreshes its own catalog, and `KNOWN_PKS` (the ~1,050-entry hardcoded seed list) accumulates both the old and the new pk for the same screener over time. - **A provider-issued id column that silently holds the SYMBOL instead of the provider's id is a permanent, self-concealing 404.** `nse_stocks.tlid` held the ticker for 412 of 2,234 rows, so every Trendlyne fetcher built `.../adv-technical-analysis/AARTECH/24/` and failed forever for 18.4% of the universe — while also burning 3 `retry_get` attempts with exponential backoff per row per run, which inflated the reported failure rate enough that a REAL transient upstream outage was indistinguishable from the standing noise floor. **Tell:** `SELECT count(*) FROM t WHERE provider_id !~ '^[0-9]+$'` (or whatever the provider's id shape is) on any column `data-sources.md` describes as opaque/numeric. Do not filter these out silently — log the count, or the gap becomes invisible instead of merely broken. Same root cause as the composite-key collisions: a column whose values are not what its name promises, with no constraint expressing the difference.

- **`.iloc[-N:]` on a long `(symbol, date)` panel slices the last N ROWS, not the last N DATES — and it is silently wrong every time a table has more than one row per date.** `drift_detector.py`'s `check_feature_drift()` took `df.iloc[-30:]` meaning "last 30 days" (its own docstring says so), but `feature_store` has ~2,400 rows per date, so it sliced the last 30 *symbols of a single date*. Any market-wide column broadcast identically to every symbol on a date (`fii_10d_net`, `dxy`, `nifty_vix`, …) then had near-zero variance in that single-date sample against a real multi-date baseline, pinning PSI far above the critical threshold on every run regardless of actual drift — found 2026-08-14 via routine log review: `EMERGENCY_RETRAIN` had fired every single day since at least 2026-08-01, `max_psi` stuck at ~12.4-12.9 (real drift moves; this didn't). Not cosmetic: `scoring_engine.py` reads the same `drift_score` and applied a real 0.85x haircut to every stock's `win_probability` whenever it exceeded `PSI_CRIT` — this was very likely permanently active for weeks. Fixed by slicing on `df["date"].isin(...)` against the sorted distinct dates instead of row position. **Tell:** any `.iloc[-N:]`/`.head(N)`/`.tail(N)` on a dataframe read from a table that isn't one-row-per-date — check `information_schema` or just `df['some_key'].value_counts()` before trusting a row-based window means what its comment says. Same family as measurement.md's "judge a datasource by dates PER SYMBOL, never by raw row count" panel-shape rule, in monitoring-script form rather than a backtest.

- **A timestamp used as a uniqueness key is only as fine-grained as the SYSTEM CLOCK TICK, not as its ISO output implies — and when the key collides behind `ON CONFLICT DO NOTHING`, an entire write is discarded silently.** `unified_ranker.run()` stamped `generated_at = datetime.now(timezone.utc)`; `unified_recommendations_history` is `PRIMARY KEY (symbol, generated_at)` with `ON CONFLICT DO NOTHING` *deliberately*, because rewriting a snapshot is the failure that table exists to prevent. Measured 2026-08-15: `time.get_clock_info('time').resolution` is **0.015625 s** on Windows and 2,000 back-to-back `datetime.now(timezone.utc)` calls returned **exactly ONE distinct value**. `run()` over a small universe finishes well inside one tick, so two runs in quick succession shared a timestamp and the second run's whole snapshot vanished — no error, no warning, no row-count change. Fixed with `_next_generated_at()` (bump 1µs on collision, keeps a true wall-clock value because the pre-market provenance filter depends on it). **Tell:** any column that is BOTH a wall-clock timestamp AND part of a uniqueness constraint. Ask what happens when two writes land in the same tick — and note the answer differs per platform (Linux ~1 ns, Windows 15.6 ms), so "it never happens in production" can be true while dev is broken, or the reverse. Same family as this file's provenance-column entries: a column whose values are not as precise as its name promises.

- **A test dismissed as an "order-dependent flake" can be a real defect whose trigger is timing.** `test_history_snapshot_is_append_only_across_reruns` was recorded across multiple sessions as a known flake that "passes standalone" — it was reporting the `generated_at` collision above the entire time. Test ordering only changed how much wall-clock elapsed between the two `run()` calls, i.e. whether they landed in the same clock tick. Two traps this cost: (1) running it with `-s` made it PASS, because the added print I/O widened the gap — instrumentation that changes timing can hide a timing bug; (2) the first plausible root cause (SQLite truncating the timestamp on write) was **wrong**, disproved by actually storing two microsecond-separated datetimes and reading back 2 distinct rows. **Before labelling a test flaky, reproduce it deterministically and read the actual assertion message.** Here it was `expected 2 distinct generated_at, got 1` — which names the bug outright, and had been visible in every failing run for weeks. A file containing nothing but five `assert True` statements reproduced the failure identically, which is what proved the trigger was suite composition/timing rather than any test's content.

## Monitoring blind spots

- **A table-freshness check cannot see whether the FEATURE that table exists to produce ever landed.** These are different questions and this repo had ~90 checks answering only the first. Measured 2026-08-12: `extra_endpoint_responses` took 21,461 fresh rows a night (check passes, green) while all 14 `ext_*` columns it feeds were 0% populated; platform-wide, 21 of `ml_ensemble.py`'s 254 declared `technical_signals` inputs were 100% NULL on every one of the last 10 trading dates — i.e. a hardcoded default fed to every stock — and 106 more were under 50%, with the monitor reading 86 pass / 1 fail throughout. **A fresh table is not a delivered feature.** `technical-signals-feature-coverage` now counts 100%-NULL columns on the last COMPLETED day (generic, via `jsonb_each` over the row — an enumerated column list would only ever guard what someone remembered to add). When adding a fetcher whose whole purpose is to stamp a column, the freshness check on its own table is necessary and not sufficient.

- **A data-quality check's own assumption goes stale, silently, when the source logic it guards grows a new legitimate case.** `unified-recommendations-trading-day` tested "does `computed_at` have a matching `stock_ohlcv` row" — correct when the only way to get a bad `computed_at` was a weekend/holiday mislabel (all such dates are permanently unbacked). `as_of.logical_session_date()` later (2026-08-12) gained a second, legitimate behavior: rolling a post-open run forward to the *next* session, so a real evening re-run correctly stamps tomorrow's date — a real future weekday that simply has no bar *yet*. The check couldn't tell that apart from a true mislabel and fired every night until the bar landed (caught live 2026-08-13, one snapshot/2,188 rows on a Friday). Fixed by splitting the predicate: a weekend is knowable bad in advance (`EXTRACT(ISODOW) IN (6,7)`); a non-weekend date only counts as bad once it's strictly in the past and still unbacked. **Different shape from the freshness-vs-feature blind spot above** — that one is a check answering a too-narrow question; this one is a check whose answer was correct on the day it was written and silently stopped being correct when a dependency's semantics changed underneath it. When editing any date/provenance-rollforward function (`as_of.py`, `logical_*`), grep for every data-quality check reading the column it stamps — a check's SQL doesn't know when its premise changes.

## Investigating production without breaking it

- **A client-side timeout does NOT cancel the server-side query — it orphans it, and on a big table that orphan can block the whole platform.** Hit 2026-08-15 while auditing: a `timeout 20 node -e "...SELECT ... FROM unified_recommendations WHERE computed_at::date NOT IN (SELECT date FROM stock_ohlcv)..."` returned to the shell after 20s looking like a harmless failed probe. The **Postgres backend kept executing it for 2h15m**, holding a relation lock that 30 subsequent queries queued behind — including the platform's own nightly `MAX(date) FROM stock_ohlcv` job steps, some waiting ~56 minutes. Every later attempt to read `stock_ohlcv` hung, which was then **misdiagnosed as TimescaleDB decompression cost** and used to justify abandoning a measurement as "not feasible" — a wrong technical conclusion built entirely on self-inflicted lock contention. After `pg_cancel_backend`, the identical `count(*)` that had been hanging returned in **0.7s**. **Tells:** any query that "hangs" on one specific table while other tables respond normally is lock contention until proven otherwise — never a storage-engine theory. **Diagnose before theorising:** `SELECT pid, wait_event_type, wait_event, now()-query_start, pg_blocking_pids(pid), query FROM pg_stat_activity WHERE state <> 'idle'` — `wait_event_type = 'Lock'` across many rows plus one long-running root with `cardinality(pg_blocking_pids(pid)) = 0` is the whole answer in one query. **Prevent it:** set a server-side bound (`SET LOCAL statement_timeout = '30s'`) on any ad-hoc investigative query, rather than relying on a client-side `timeout`, and prefer `EXPLAIN` / a bounded `LIMIT` over an unbounded `NOT IN (SELECT ...)` anti-join against a multi-million-row table. Same family as this file's "verify the connection before trusting the result" entry: the shell's view of what happened is not the database's.

- **A migration's own "files remaining" counter cannot count the files it never reaches.** The SQLite decommission's shim printed `[sqlite-decommission] 37 test files still reach Postgres through the sqlite3.connect shim`, and that number was trusted across sessions as the size of the remaining job. It was installed by an autouse fixture in `src/server/tests/conftest.py`, so it only ever saw tests under that directory — while `src/server/__tests__/` (which reads like the vitest directory, and mostly is) holds ~20 `test_*.py` files with **no conftest.py of its own**. Those ran on real in-memory SQLite for their entire lives, were never shimmed, never appeared in the counter, and were exactly the files most likely to hide a dialect bug: moving them onto Postgres produced 50 failures immediately. **Tell:** any progress metric emitted by the mechanism whose coverage it is measuring. Derive the count from the source tree (`grep -rl` over the whole repo) and assert it equals what the instrument reports — same shape as this file's "a guard test built on a hand-enumerated allowlist only guards what someone remembered to list" entry.

- **A test that WRITES through one engine and READS through another asserts nothing, and looks green while doing it.** 14 vitest files seeded fixtures with `better-sqlite3` (`db.prepare(...).run(...)` against `db.ts`) and then read the result back through a tRPC caller, which routes via `dbAsync`. As long as both ended up on SQLite this was invisible. The instant the read side moved to Postgres (SQLITE_DECOMMISSION_PLAN Phase 2, 2026-08-16) they failed as "expected +0 to be 1" — the writes had been going somewhere the assertions never looked. **Tell:** a test file that imports BOTH a raw driver (`../db`, `sqlite3.connect`) and an app-level accessor (`../dbAsync`, a router caller, a service function). Pick one; if the code under test uses the facade, the fixture must too.
- **Moving the test substrate onto the real dialect is not fixture churn — budget for real production bugs, because the SQLite path structurally cannot fail on them.** The Phase 2 TS conversion found three, all live, all green under SQLite for their entire lives: (1) `scoringService` wrote `timeframe_scores.updated_at`, a column production has never had (real name `computed_at`) — the live table held **0 rows** because every write had always failed; (2) the same upsert's `ON CONFLICT(symbol, timeframe)` matched no constraint, since the live PK is `(symbol, timeframe, run_id)` and one code path passed `run_id = null`; (3) `backtestRunner` called `.slice()` on `screener_runs.run_ts`, a TIMESTAMPTZ that node-postgres hands back as a `Date`, so every `runId`-scoped backtest threw `.slice is not a function`. All three were mis-declared in `db.ts`, i.e. concrete instances of this file's own "a column type assumed from `db.ts`" entry — that file described 147 of live's 212 tables and was wrong about the ones it did describe. `db.ts` is now `db.sqlite-legacy.ts`, imported by nothing.
- **A test parser that reads another file by PATH and swallows the read error degrades silently, and the failure surfaces somewhere unrelated.** `test_fundamentals_pit.py` scrapes ~160 `ALTER TABLE technical_signals ADD COLUMN` statements out of `db.ts` (plus every `.py` engine) to build its mock schema, inside a `try: open(path) ... except OSError: continue`. Renaming `db.ts` made that `continue` fire, the mock schema came out partial, and three tests failed with `no such column: ts.news_sentiment_score` — a message that reads like schema drift, not a missing input file. Worse, it only reproduced in some run orders. **Any parser that reads a sibling source file by hardcoded path needs an `assert exists`, not an `except: continue`** — a missing input is a broken test, not a smaller one. Same family as this file's "a guard test built on a hand-enumerated allowlist only guards what someone remembered to list."
- **`db/schema.postgres.sql` schema-qualifies its index DDL (`ON public.foo`) but not its `CREATE TABLE`s.** Applying it into any schema other than `public` therefore creates the tables where you asked and then tries to index the **production** ones. Hit 2026-08-16 building the vitest throwaway schema (`relation "idx_aar_run_date" already exists`); the file executes as one implicit transaction so it rolled back with nothing written, but that was luck of the error, not isolation. Rewrite `public.` before applying it anywhere but `public`, and assert none survived. Note also that the file is only as good as its last regeneration — `trendlyne_stock_metrics_history` was live but absent from it (added by `4b022ec`, never reflected back), and it is now the source the entire vitest suite's schema is built from, so `npm run schema:drift` is a test-correctness check and not just tidiness.

## Environment & deploy

- **Declared ≠ installed.** `node-pg-migrate` in `package.json` but not `npm install`ed; `nse` in `requirements.txt` but not in the venv. Both silently broke a live job for days.
- **Written ≠ applied.** A migration verified against a throwaway local cluster is not applied to production. Confirm `npm run migrate:up` ran against the real `POSTGRES_URL`.
- **Committed ≠ deployed.** `.ts` is not hot-reloaded; `pm2 restart bharat-server` is required. Check `pm_uptime` against the fix commit's timestamp before believing a fix is live.
- **A standalone `tsx` script that imports `dbAsync` without `import 'dotenv/config'` silently talks to SQLite, not production Postgres — and it will happily print convincing numbers.** `USE_POSTGRES` lives in `.env`, which the pm2 server loads at boot but a hand-run script does not, so the facade falls back to the dev SQLite DB. Hit 2026-08-12 while "live-verifying" a fix: the script reported 121,669 `screener_appearances` rows for Trendlyne and 26 carrying the new column; Postgres actually had **435,700 rows and 0**. It even resolved a *different* `screenpk` for the same screener (24700 vs 358883), which is the cheapest tell. **Verify the connection before trusting the result** — print `process.env.USE_POSTGRES` and assert a row count against a figure you already know from `psql`/`db_compat`. Same family as the two-venvs trap below. `PYTHON_PATH=backend-python/venv` is what production uses. Bare `python` on PATH is a different install with a different sklearn. Never run a training script with the wrong one.
  **STRUCTURALLY FIXED 2026-08-15 — this entry is now history, not a live hazard.** The root cause was that the dialect *defaulted to SQLite*: `pgConfig.ts`'s `usePostgres()` and `sql_translate.py`'s `use_postgres()` both read `USE_POSTGRES === 'true'`, so any process that did not load `.env` silently chose the stale local `database.sqlite` (3.49 GB, measured ~2 months behind production: `unified_recommendations` max 2026-06-19 vs 2026-08-17 live). Both now return Postgres unconditionally for every real process, consulting no environment variable at all; the SQLite fixture is reachable only inside a test runner (`process.env.VITEST` / `"pytest" in sys.modules` — runner-owned markers `.env` cannot forge) **and** with an explicit opt-in. Verified in a clean interpreter: `USE_POSTGRES` unset → Postgres, `=false` → Postgres, `=0` → Postgres. Pinned by `src/server/__tests__/postgresOnly.test.ts` and the "Postgres-only guarantee" block in `src/server/tests/test_sql_translate.py`, both negative-controlled (3 TS / 5 Python tests fail against the old default) plus a cross-language test that fails if the TS and Python rules ever drift. **Also corrected: `infra_gotchas`' "AlphaQuant writing SQLite" was never true** — `pcr_engine.py`/`portfolio_analytics.py` carried two dead `sqlite:///`-forcing lines they never referenced (both call `get_engine()`, which honours the dialect); deleted, and live-verified that they resolve to `postgresql+psycopg2`. **The general lesson survives the fix: a fallback that answers is worse than one that fails.** When a default exists for "which backend/credential/model do I use", make the *safe* option the default and the *degraded* one require an explicit, forgery-resistant opt-in — otherwise a missing variable becomes a confident wrong answer instead of an error.
- **A manual `UPDATE app_settings` is not a fix.** It reverts on any fresh DB and is invisible to every other environment. Seed it in a migration.

- **Deleting a thing does not delete the checks and instructions that point at it — and an orphaned check does not go quiet, it starts emitting false signals in the opposite direction.** The 2026-08-15 Postgres-only change removed `USE_POSTGRES` from every real code path. What survived it, found by a docs sweep on 2026-08-16 rather than by any failure: (a) **eight live instruction files** — 4 `.claude/commands/*`, 3 `.claude/skills/*`, `README.md` — still told the reader to `print process.env.USE_POSTGRES` to confirm they were not on SQLite. That check now returns `undefined` on a **correct** script, so the documented remedy indicts working code and exonerates nothing; the entry directly above it in this very file had already been marked "history, not a live hazard" and the downstream copies were never swept. (b) **`envConfig.ts:23-35` still hard-exits** the server on a mistyped `USE_POSTGRES`, justified in its own comment by a SQLite fallback that no longer exists — so a stale `USE_POSTGRES=1` in someone's `.env` now crashes `bharat-server` at boot over a variable that routes nothing (AF-20260816-09). (c) `confluence.router.ts` carried a comment explaining a per-call env read that no longer happens. **Same family as this file's "monitor that fires on every run carries no information" and "a data-quality check's own assumption goes stale" entries, but triggered by a deletion rather than by drift.** The deletion is the cheapest moment to catch it and the one nobody budgets for. **When you remove an env var, a column, a file, or a fallback, the change is not done at the last code edit — grep the removed identifier across `.md`, `.claude/commands/`, `.claude/skills/`, and validator/bootstrap code, and treat every hit as either a fix or a deliberate historical note with a dated banner.** A retired file needs the same treatment: `db.ts` → `db.sqlite-legacy.ts` left "mirror it into `db.ts`" and "check the column type in `db.ts`" standing as live advice in the review commands.

## Testing

- **A warning printed by a test runner is not a verdict — CI, git hooks and `verify-gate.mjs` all read the EXIT CODE.** When the Python suite could not reach Postgres it skipped every test that needed one, printed a loud `WARNING: N test files were SKIPPED`, and **exited 0**. So the guard written specifically to stop "green while protecting nothing" was itself only advisory: any automation consuming that run saw success. Fixed 2026-08-17 — `pytest_sessionfinish` flips the exit code to 1 whenever a test was skipped for an unreachable database (individual tests still *skip* rather than error, so the output stays readable; it is the run's verdict that changes). **The tell was an asymmetry between two runners with the same hard requirement**: `vitest.globalSetup.ts` already THREW when it could not reach Postgres, so the TS half could not silently degrade and the Python half could — same repo, same dependency, two different answers, and nobody had compared them. Pinned by `TestUnreachablePostgresCannotExitZero` in `test_pg_db_fixture.py`, which drives conftest's real hook (not a reimplementation) and includes the control that an already-failing run keeps its own status. **When two runners/services depend on the same thing, diff how each one behaves when that thing is missing.**
- **A `live_datasource`-gated test is code that DOES NOT RUN, so it rots silently — and the rot is invisible to every check this repo has.** The gate is correct and must stay (a third-party outage must never redden CI, per `data-sources.md`), but it means those files are never executed by `pytest`, `vitest`, CI, or a pre-commit hook. Running all 230 by hand on 2026-08-17 — the first time in an unknown while — gave **3 failures, and only one was an upstream blip**: (1) `test_live_datasource_intraday_fetcher.py`'s `_CaptureDB.query_all` stub returned the SAME rows for every query regardless of SQL; `_known_open_days()` was added to `intraday_fetcher.py` five days after the stub was written (`e8aac43`, 2026-08-10) and issued a second, differently-shaped query, so the stub handed it symbol rows with no `datetime` key → `KeyError`. **Broken for 7 days, nothing noticed.** (2) `test_live_datasource_nse_ipo_calendar.py` still hand-rolled `INSERT OR REPLACE`, which `translate()` rejects by design — broken the moment its fixture moved onto Postgres in the same-day Phase 2 conversion, and the conversion's own full-suite verification could not see it. (3) `ndtv_fno_basis` returned an empty list from upstream and passed on retry — the genuine transient the gate exists for. **Two lessons: a stub that ignores its input answers questions it was never taught, confidently and wrongly (dispatch on the SQL/URL so an unexpected call fails loudly instead of receiving someone else's rows); and any bulk change touching test fixtures must state explicitly which of the converted files it did not execute.** Run the live suite by hand after any sweep that edits them, and treat its failures as three separate questions — my code, their code, or their server — not one.
- **Negative-control every new test**: revert the fix, confirm the test fails, restore. Three separate suites here were 100% green while protecting nothing.
- **A test that reimplements the logic under test** passes against the unfixed source. Call the real function. **Recurred 2026-08-13**: a regression test for `screener_catalog_enricher.py`'s category-collapse bug hand-copied the `cat_norm`/`CATEGORY_DEFAULTS` resolution logic into the test file itself instead of importing it — negative-controlling the *source* left the test green, because the mirror never saw the fix or the bug. Caught only by insisting on negative-controlling every new test per the rule above; fixed by extracting the real logic into an importable `resolve_screener_defaults()` and calling that.
- **A test that derives its expectation from the constant it is testing** passes vacuously (`all([])` is `True`).
- **A test that relies on a library's inferred default** to manufacture its own precondition silently stops testing anything when the library changes. Construct the condition explicitly.
- **Env vars a shared facade reads are shared state.** `USE_POSTGRES` is read fresh per call; a suite running in one process leaks whichever file set it last. Pin it in the fixture. **Same class, TS-specific instance, 2026-08-13**: a static top-level `import 'dotenv/config'` in a new live-datasource test file loads real credentials into `process.env` for the entire vitest worker process the moment the file is *collected*, not just when it *runs* — so even a `describe.runIf(RUN_LIVE)`-skipped suite still pollutes every other test file sharing that worker. Broke `niftytraderAuthService.test.ts`'s "no credentials configured" case this way (a real `NIFTYTRADER_EMAIL`/`PASSWORD` from `.env` overrode the test's own `delete process.env...`). Fix: check the plain shell env var (`RUN_LIVE_DATASOURCE_TESTS`, not anything `.env` provides) first, and only `await import('dotenv/config')` conditionally inside that guard — never as a static top-level import in a file that might load real secrets other tests don't expect.
- **A config env var that a library snapshots at IMPORT time is a no-op if you set it after the import — it fails open, and the obvious test for it passes against the broken ordering.** `huggingface_hub` reads `HF_HUB_OFFLINE` into `huggingface_hub.constants` once, when it is imported. So `os.environ.setdefault("HF_HUB_OFFLINE", "1")` placed *below* `from transformers import pipeline` sets the variable and changes nothing: FinBERT still loads, it just silently goes back to calling the Hub on every process start (2026-08-17 — `nlp_engine.py`, `finbert_scorer.py`; the tell was `bharat-server` logging every `finbert_news_sentiment.py` run as "finished successfully with warnings/stderr output", 268 bytes of `unauthenticated requests to the HF Hub` + tqdm bar, for a model already complete in the local cache). **The testing half is the part that recurs:** the natural assertion — `os.environ["HF_HUB_OFFLINE"] == "1"` after importing the module — passes *identically* against the broken ordering, because `setdefault` sets the var either way. The env var is not the thing that matters; the library's **resolved constant** is. Assert `huggingface_hub.constants.HF_HUB_OFFLINE` (in a clean subprocess with the var popped), not `os.environ` — `test_finbert_offline_load.py`, negative-controlled: importing transformers first leaves the constant `False`, which the `os.environ` form could not detect. Same family as the `dotenv/config`-at-collection-time entry above (env × import timing) and as "a test that derives its expectation from the constant it is testing" (an assertion that cannot fail against the bug). **Tell:** any env var set for a third-party library's benefit — grep whether that library reads it once at import (`constants.py`, a module-level `os.getenv`) or fresh per call; only the second kind tolerates being set late. Note `local_files_only=True` is *not* the fix here: transformers 5.9.0's `pipeline()` has no such parameter, it lands in `**kwargs`, and the Hub call still happens.
- **A guard test built on a hand-enumerated allowlist only guards what someone remembered to list.** `screenerAppearedAt.test.ts` opened with "pins that all three screener syncs record `appeared_at`" and listed three — there are **four** writers, and the omitted one (`trendlyneScreener.ts`) is the largest, 435,700 of the table's 741,251 rows. Result: `appeared_at` was populated on **10 rows platform-wide** while the suite stayed green and the column looked delivered. Same shape as the "grep EVERY reader of the table" rule above, in test clothing. Derive the list from the source tree (scan for the INSERT/call and assert the scan equals the allowlist) so adding a 5th provider fails the test instead of silently writing NULLs forever.
